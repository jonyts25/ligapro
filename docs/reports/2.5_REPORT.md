# Reporte paso 2.5 — Calendario de reservas + rentas particulares

## Resumen

Nueva pantalla `/canchas/calendario` con selector de semana, grilla canchas × días × horas y reservas `confirmed` como bloques. Alta de reservas no-partido (`maintenance`, `private_rental`, `closed`, `manual_block`) vía INSERT directo bajo RLS existente; cancelación soft (`status = 'cancelled'`). Partidos se muestran read-only con enlace al detalle. **No se requirió migración**: constraints EXCLUDE, trigger padre/hijo (2.4) y RLS owner/admin ya cubren el caso.

## Migración

**No aplica.** Se usó INSERT/UPDATE directo sobre `field_reservations` con las validaciones ya existentes en DB (traslapes, padre/hijo, CHECK de tipos). La restricción de no cancelar `match` desde esta pantalla se implementó en server action (mensaje claro) sin RLS adicional — el UPDATE genérico de admin podría técnicamente cancelar un partido, pero la UI y la acción lo impiden; un refuerzo RLS sería opcional en un paso futuro si se desea blindaje en DB.

## Pruebas manuales para Jonathan

1. Ir a **Canchas → Calendario** → semana actual visible.
2. **Nueva reserva** → renta particular en cancha libre → aparece bloque en grilla.
3. Intentar otra reserva que se traslape con un **partido** existente → error Postgres en español (EXCLUDE o padre/hijo).
4. Abrir la renta → **Cancelar** → desaparece de la grilla (soft cancel).
5. Clic en bloque **Partido** → enlace a detalle del partido; sin botón cancelar.

## Riesgos o dudas

- Cancelación de `match` no está bloqueada en RLS, solo en la acción/UI.
- La grilla usa celdas por hora; reservas cortas (&lt;1 h) ocupan la hora de inicio.
