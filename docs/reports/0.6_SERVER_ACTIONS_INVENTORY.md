## Leyenda de categorías

| Cat. | Significado |
| --- | --- |
| **A** | Solo RPC o cliente Supabase con RLS; sin secretos, sin `redirect()`, sin generación de tokens/URLs de invitación, sin checks de platform staff. `revalidatePath` no cuenta. |
| **B** | Depende de secretos, email, tokens, `redirect()`, cookies/server session de formas que mobile no replica, platform staff, subida especial de archivos, o es puramente infra Next.js (revalidate-only / redirect-only). |
| **C** | Mixto: núcleo RPC/RLS portable + capa servidor (admin gate extra, redirect, prompt/URL, generación fixture, tier limits, lecturas auxiliares, etc.). Detalle en columna *dependencia servidor*. |

## Leyenda app fase 1

Fase 1 mobile = **árbitro/anotador**: capturar eventos, cerrar partido, confirmar asignación, listado «mis partidos», validación/consulta de plantel.

| Valor | Significado |
| --- | --- |

| **no** | Fuera de alcance fase 1 (admin web, plataforma, finanzas, invitaciones, etc.). |
| **después** | No bloqueante fase 1; fases posteriores del producto mobile. |

## Estado fase 1 — brechas resueltas

1. **Confirmar asignación (oficial):** resuelto. Existe RPC `confirm_match_official` y acción `confirmOwnMatchOfficialAction` (self-service miembro → `confirmed`). `confirmMatchOfficialAction` sigue siendo admin-only para confirmar a terceros.

3. **Mis partidos:** resuelto en web. Ruta `src/app/(protected)/organizaciones/[organizationId]/mis-partidos/page.tsx` usa `getMyOfficialMatchAssignments`. Nav item en `nav-items.ts`.

4. **Auth mobile:** sin cambio — login/logout vía `@supabase/supabase-js` en dispositivo; no reutilizar acciones `auth/actions.ts` (Category B).

5. **Invitados arbitrales:** flujos token en `matches/guest-actions.ts` (Category **B**); fuera de alcance app mobile autenticada fase 1.

## Endpoints `/api/mobile` — orientación actualizada

No existen rutas `/api/mobile/*` hoy (`src/app/api/` solo export/health). Para fase 1 (árbitro/anotador autenticado):

### Operaciones core — Category A directo (supabase-js)

Mobile con JWT puede llamar los mismos RPC que las acciones Cat. A/C portables, **sin** route handlers POST obligatorios:

| Operación fase 1 | RPC / lectura directa | Acción web equivalente |
| --- | --- | --- |
| Listar mis partidos | `getMyOfficialMatchAssignments` (queries) o SELECT RLS `match_officials` + joins | — (lectura) |
| Confirmar asistencia | `confirm_match_official` | `confirmOwnMatchOfficialAction` |
| Registrar evento | `can_capture_match` + `record_match_event` | `recordMatchEventAction` |
| Cerrar partido | `update_match_result` (con permisos árbitro en RPC/RLS) | `updateMatchResultAction` |

**No se requieren** rutas POST obligatorias `/api/mobile/.../confirm`, `/api/mobile/.../result` ni `/api/mobile/.../events` si la app usa supabase-js con sesión del usuario.

## Notas de portabilidad mobile

- **Category A (43):** mobile con JWT Supabase puede invocar los mismos RPCs o SELECT/INSERT/UPDATE RLS sin pasar por Next server actions.
- **Category B (20):** no portables tal cual; reimplementar con SDK Auth nativo, omitir flujos token guest en app autenticada, o excluir de app.
- **Category C (47):** evaluar caso a caso. Acciones fase 1 (`recordMatchEventAction`, `confirmOwnMatchOfficialAction`, `updateMatchResultAction`) exponen lógica de validación en servidor que **duplica** enforcement RPC/RLS — mobile puede llamar RPC directo si policies lo permiten.
